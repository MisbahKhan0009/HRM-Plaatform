# Code review

The reviewer checks that a change is correct, secure, tested and consistent with the documented architecture. Approve only when every applicable item below holds; otherwise request changes and name the item.

## How to review

1. Read the PR description and the linked user story first. Know what the change should do before reading code.
2. Read tests before implementation: do they cover the acceptance criteria, including the negative cases?
3. Read the diff layer by layer: migration, repository, domain, service, policy, route, UI.
4. Pull the branch and run it for anything user-visible or anything touching money or permissions.
5. Comment with a label: **blocking** (must change), **question**, or **nit** (optional). Explain the why and link the rule.

## Checklist

### Correctness
- [ ] Behaviour matches the user story's acceptance criteria.
- [ ] State changes use the transitions in `docs/03-architecture/DOMAIN-MODEL.md` §5 and reject any other transition.
- [ ] Business rules live in `packages/domain` or a service, never in routes or React components.
- [ ] Enum values, role codes and permission codenames are the canonical ones.

### Security and permissions
- [ ] Every new endpoint calls the module policy with a permission and a scope (`docs/03-architecture/SECURITY-MODEL.md`).
- [ ] Self-service endpoints take the employee from the session, never from the request.
- [ ] Out-of-scope records return 404, not 403.
- [ ] Responses use a per-permission DTO; no database row is serialized directly; no salary in employee payloads.
- [ ] Input is validated with a Zod schema from `packages/contracts`.
- [ ] Privileged actions require a strong session, and sensitive actions require a recent sign-in.
- [ ] No secrets, tokens, codes or personal data in logs or audit metadata.
- [ ] Uploads check size, type and content.
- [ ] Tests include an unauthorized-role case and a cross-employee (IDOR) case.

### Data and migrations
- [ ] Migration generated by `drizzle-kit`, reviewed as SQL, forward-only, and safe on a populated table.
- [ ] No migration already on `main` was edited.
- [ ] Money columns are `NUMERIC(14,2)`; money in code uses Decimal, never `number`.
- [ ] Timestamps are `timestamptz` in UTC; business dates use `Asia/Dhaka`.
- [ ] Foreign keys that protect history use `ON DELETE RESTRICT`; no hard delete of business records.
- [ ] Writes that belong together share one transaction, with audit and outbox rows in it.
- [ ] Frequently filtered columns are indexed.

### Tests
- [ ] New logic has unit tests; new endpoints have API tests; changed behaviour has changed tests.
- [ ] Payroll and leave arithmetic has property-based or table-driven tests.
- [ ] Tests do not depend on wall-clock time or test order.

### Frontend, accessibility and i18n
- [ ] All user-visible text uses i18n keys; no hard-coded English strings.
- [ ] Components use role tokens, never raw hex values; both Ink and Paper themes checked.
- [ ] Status is never shown by colour alone.
- [ ] Keyboard focus is visible; controls have labels; forms show errors next to fields.
- [ ] Works at 360 px width for employee self-service screens.
- [ ] Hiding a button is not the only protection; the API enforces the rule.

### Cost and performance
- [ ] No new paid service or paid tier (D-032).
- [ ] No CPU-heavy work in the Worker (PDF, XLSX, large loops); see ADR-0009.
- [ ] List endpoints paginate.

### Documentation
- [ ] API, schema, config, operations or behaviour changes are reflected in the owning document.
- [ ] Product decisions are recorded in the decision log.

## Response times

Review within one working day. If a review blocks you for longer, say so in the PR; do not merge without the required approval.
