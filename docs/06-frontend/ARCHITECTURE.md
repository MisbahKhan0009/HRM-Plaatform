# Frontend architecture

`apps/web` is a client-rendered React SPA. Vite builds it to `apps/web/dist`, and the API Worker serves those files as static assets from the same origin as `/api/v1` (ADR-0002, ADR-0005). There is no server-side rendering. This file defines how routing, auth, data fetching, errors and features are organised.

## 1. Folder layout

```text
apps/web/
├── index.html                 # contains the no-flash theme script (THEMING-AND-TOKENS.md section 4)
├── vite.config.ts             # React, TanStack Router plugin, Tailwind v4 plugin
└── src/
    ├── main.tsx               # createRoot, providers, router
    ├── router.tsx             # createRouter with context { queryClient, auth }
    ├── routeTree.gen.ts       # generated by the TanStack Router plugin, committed, never edited
    ├── routes/
    │   ├── __root.tsx         # root: error boundary, toaster, title updater, route announcer
    │   ├── (auth)/            # sign-in, verify, two-factor, accept-invite, recover
    │   ├── _app.tsx           # authenticated layout: guard + AppShell (sidebar, top bar)
    │   └── _app/              # one folder per section (INFORMATION-ARCHITECTURE.md section 1)
    ├── features/<module>/     # module code used by routes (section 6)
    ├── components/            # app-level composites: AppShell, Sidebar, TopBar, PageHeader, RouteError
    └── lib/
        ├── api/               # fetch client, problem+json parsing, query keys
        ├── auth/              # current user query, capability helpers, step-up handling
        ├── query-client.ts
        ├── theme.ts
        ├── format.ts          # thin wrappers over Intl (I18N.md)
        └── i18n.ts
```

Module folders under `features/` use the backend module names from `docs/03-architecture/DOMAIN-MODEL.md` section 1: `accounts`, `organization`, `employees`, `attendance`, `leave`, `payroll`, `reimbursements`, `documents`, `approvals`, `reports`, `audit`, `settings`. `notifications` has no UI module in v1 (email only, D-025).

## 2. Routing

- **TanStack Router, file-based**, with the Vite plugin generating `routeTree.gen.ts`. Paths match INFORMATION-ARCHITECTURE.md section 1 exactly.
- Route files stay thin: `validateSearch` (Zod), `beforeLoad` (guard), `loader` (prefetch queries), and a component that renders a feature page. No fetch calls or business logic in route files.
- **Search params are state.** Filters, sorting, pagination, tabs and selected dates live in typed search params validated with Zod (`validateSearch`), so URLs are shareable and the back button works. See TABLES-AND-LISTS.md section 3.
- **Code splitting**: every route component is lazy (`.lazy.tsx` or automatic splitting in the plugin). Heavy libraries (`pdf-lib`, `exceljs`) are dynamically imported at the moment of use (`docs/07-quality/PERFORMANCE-BUDGETS.md`).
- **Preloading**: `defaultPreload: 'intent'` so hovering or focusing a link preloads its route code and loader data; `defaultPreloadStaleTime: 0` so TanStack Query owns freshness (tanstack-router-query skill).
- **Scroll restoration** on; focus moves to the page `h1` after navigation and the title is announced (ACCESSIBILITY.md section 5).

## 3. Authentication and guards

- The session is an HttpOnly cookie set by Better Auth. The SPA never reads or stores tokens.
- **Current user**: `GET /auth/me` returns `CurrentUser` (identity, employee link, roles, permissions, `strongAuth`, theme, locale). It is fetched with TanStack Query key `['auth', 'me']`, `staleTime: 5 min`, refetched on window focus.
- **`_app.tsx` guard** (`beforeLoad`): `ensureQueryData(['auth','me'])`; on `401 UNAUTHENTICATED` redirect to `/sign-in?redirect=<current path>`. If the user has a privileged role and no strong factor enrolled, redirect to the enrolment gate (`/me/security?enrol=1`, USER-FLOWS.md 1.3).
- **Per-route guards** use the permission table in INFORMATION-ARCHITECTURE.md section 2:

```ts
beforeLoad: ({ context }) => requireAny(context, ['leave.read.team', 'leave.read.all'])
```

  `requireAny` throws `notFound()` when the user lacks every listed permission, so the user sees the same 404 as the API gives for out-of-scope records.
- **Capability helpers** (`lib/auth`): `useCan('payroll.approve')`, `can(user, 'employee.read.all')`. Components use them only to hide or disable actions. Permission strings come from `@hrm/contracts` as a typed union, so a typo is a type error.
- **Step-up**: the API client intercepts `403 MFA_REQUIRED` and `403 REAUTH_REQUIRED`, opens the step-up dialog (USER-FLOWS.md 1.4) through a global store, waits for the result and retries the original request once with the same `Idempotency-Key`. If the user cancels, the original promise rejects with a `StepUpCancelledError` that features treat as "no change".
- **Sign-out**: `POST /auth/sign-out`, then `queryClient.clear()`, then navigate to `/sign-in`. A `401` on any request after sign-in clears the cache and redirects the same way.

## 4. API client

- `lib/api/client.ts` wraps `fetch` with: base path `/api/v1`, `credentials: 'same-origin'`, JSON headers, `Idempotency-Key` header when the caller passes `idempotent: true` (generated with `crypto.randomUUID()` once per user action and reused on retry), and `AbortSignal` support from TanStack Query.
- Every state-changing request is same-origin, so the browser sends the `Origin` header the CSRF middleware checks (API-STANDARDS.md section 4). Never set `mode: 'no-cors'` or call the API from another origin.
- Request and response types come from **`@hrm/contracts`** (Zod schemas and inferred types shared with the API). Responses are parsed with the contract schema in development and test builds to catch drift early; production skips the parse for performance and trusts the typed response.
- Errors: non-2xx responses with `application/problem+json` become an `ApiError` with `status`, `code`, `title`, `errors[]` (field issues with JSON Pointer `path`) and `requestId` (from the response header). Network failures become `NetworkError`. Nothing else is thrown.
- Money and dates arrive as strings (`"45000.00"`, `"2026-10-22"`, ISO timestamps) and stay strings in the cache. Formatting happens at render time (I18N.md section 5).

### 4.1 Feature API modules

Each feature has `features/<module>/api.ts` exporting query option factories and mutation hooks. Example shape:

```ts
export const leaveQueries = {
  all: () => ['leave'] as const,
  balancesMe: () => queryOptions({ queryKey: [...leaveQueries.all(), 'balances', 'me'], queryFn: getMyBalances }),
  requests: (params: LeaveRequestListParams) =>
    queryOptions({ queryKey: [...leaveQueries.all(), 'requests', params], queryFn: () => listLeaveRequests(params) }),
  request: (id: string) => queryOptions({ queryKey: [...leaveQueries.all(), 'request', id], queryFn: () => getLeaveRequest(id) }),
}
```

## 5. Server state with TanStack Query

| Setting | Value | Why |
|---|---|---|
| `staleTime` default | 30 s | Data changes through user actions we invalidate explicitly |
| `gcTime` | 10 min | |
| `retry` | 1 for queries on network errors and 5xx; never on 4xx; mutations never retry automatically | Avoid duplicate side effects |
| `refetchOnWindowFocus` | true | People leave tabs open all day |
| Approval inbox count | `refetchInterval: 60 s` while the tab is visible | INFORMATION-ARCHITECTURE.md section 4.1 |

**Query keys** are hierarchical arrays starting with the module name: `['leave','requests',params]`, `['payroll','run',id]`, `['payroll','run',id,'items',params]`. List params are the validated search-param object, so the cache key matches the URL.

**Invalidation after mutations** (in the mutation's `onSuccess`, never by manual cache edits for server-computed values):

| Mutation | Invalidate |
|---|---|
| Check in / out | `['attendance']`, dashboard widgets under `['dashboard']` |
| Leave submit, withdraw, approve, reject, cancel | `['leave']`, `['approvals']` |
| Correction submit, approve, reject | `['attendance']`, `['approvals']` |
| Claim submit, approve, reject, withdraw | `['reimbursements']`, `['approvals']` |
| Any payroll run transition | `['payroll','run',id]`, `['payroll','runs']`, `['approvals']`, `['reimbursements']` |
| Profile change approve | `['employees', id]`, `['auth','me']` |
| Preferences | `setQueryData(['auth','me'], response)` (the response is the full `CurrentUser`) |

Optimistic updates are allowed only for preferences (theme). Everything involving balances, money or status waits for the server.

Use `useSuspenseQuery` with route loaders (`ensureQueryData`) for page-level data and `useQuery` for widgets that load independently (dashboard). Pending UI is skeletons, not spinners (COMPONENT-SPECS.md section 14).

## 6. Feature folder anatomy

```text
features/leave/
├── api.ts                     # query options, mutation hooks (section 4.1)
├── pages/                     # page components rendered by routes: MyLeavePage, LeaveRequestPage …
├── components/                # feature components: LeaveBalanceBar, LeaveRequestForm, LeaveStatusBadge …
├── forms/                     # form wiring: schemas imported from @hrm/contracts, default values, mappers
├── tables/                    # column definitions for TanStack Table
└── index.ts                   # public exports used by routes and other features
```

- A feature may import from `@hrm/ui`, `@hrm/contracts`, `@hrm/i18n`, `@hrm/documents`, `lib/*` and another feature's `index.ts`. Never deep-import another feature's internals.
- Cross-module screens (dashboard, approvals detail) compose components exported by each feature (for example the approval detail renders `leave`'s `LeaveRequestSummary` for `subjectType = leave_request`).

## 7. Errors

- **Root error boundary** (`__root.tsx` `errorComponent`): unexpected render errors show the error page (brand moment) with the request id if known and a **Reload** button; the error is reported to Sentry.
- **Route errors** (`errorComponent` per section): load failures show the inline error panel (SCREEN-INVENTORY.md section 0) inside the shell, keeping navigation usable.
- `notFound()` from guards or `404 NOT_FOUND` from loaders renders the 404 page.
- **Mutation errors** are handled where the action happens: field errors in forms (FORMS-AND-VALIDATION.md), inline alerts for page actions, toasts for row actions. Message text is chosen by `code` (CONTENT-STYLE.md section 6).
- `409 VERSION_CONFLICT` and `409 INVALID_TRANSITION`: invalidate the record's query, show the inline alert, keep the user's form input where possible.

## 8. Observability

- Sentry browser SDK (free plan, ADR-0008) initialised in `main.tsx` with: environment, release (git SHA), `sendDefaultPii: false`, URL scrubbing of search params, and a `beforeSend` hook that drops request bodies and any field named like `amount`, `salary`, `email`, `phone`, `nationalId`. Sample rate 1.0 for errors, tracing off (free quota, ADR-0009).
- The `requestId` from failed API calls is attached to Sentry events and shown to the user for support.
- `web-vitals` reports LCP, INP and CLS to the API logging endpoint defined by operations (`docs/08-operations/`), sampled at 10%.

## 9. Build and environment

- Environment values the SPA needs at build time are prefixed `VITE_` and contain no secrets: `VITE_SENTRY_DSN`, `VITE_RELEASE`, `VITE_ENV`. The API base path is relative (`/api/v1`) in every environment.
- Local development: `pnpm dev` runs Vite with a proxy from `/api` to `wrangler dev` so cookies stay same-origin.
- Production build: `vite build` with hashed asset names and long cache headers on `/assets/*`; `index.html` served with `no-cache`.
- Bundle budget and route-level splitting rules: `docs/07-quality/PERFORMANCE-BUDGETS.md`.

## 10. Testing

Owned by `docs/07-quality/TESTING-STRATEGY.md`. In short: feature tests with Testing Library and MSW handlers built from `@hrm/contracts` fixtures; component tests in `packages/ui` in both themes; E2E journeys with Playwright and axe.
