# Internationalisation

v1 ships in **English**; the app must be ready for **Bangla** without redesign (D-003, NFR-UX-005). This means every user-facing string is a translation key from day one, and every date, number and money value is formatted through one module that knows the locale and the company timezone. Copy rules (what the strings say) are in `docs/04-design/CONTENT-STYLE.md`.

## 1. Library and setup

- `i18next` + `react-i18next` (free, MIT). Catalogues live in `packages/i18n/locales/<locale>/<namespace>.json`.
- Locales: `en` (complete), `bn` (empty files present so missing-key tooling works; not selectable in v1).
- Namespaces = frontend modules: `common`, `auth`, `dashboard`, `attendance`, `leave`, `reimbursements`, `payroll`, `employees`, `documents`, `approvals`, `reports`, `audit`, `settings`, plus `errors` (API error codes) and `status` (enum labels).
- Namespaces are loaded per route with dynamic imports so the bundle carries only what a page needs. `common`, `errors` and `status` load at startup.
- The user's locale comes from `CurrentUser.locale` (`GET /auth/me`), falling back to `en`. `<html lang>` and `dir` are updated on change.
- TypeScript: keys are typed from the English catalogue (i18next `CustomTypeOptions`), so `t('leave.request.submitt')` is a compile error.

## 2. Key naming

Pattern: `<namespace>:<screen-or-component>.<element>[.<variant>]`, lower camel case segments.

| Key | English |
|---|---|
| `leave:request.title` | Request leave |
| `leave:request.submit` | Submit request |
| `leave:request.preview.workingDays` | {{count}} working day / {{count}} working days |
| `payroll:run.confirm.lock.title` | Lock {{period}} payroll? |
| `common:actions.cancel` | Cancel |
| `status:approved` | Approved |
| `status:cancellation_pending` | Cancellation pending |
| `errors:INSUFFICIENT_BALANCE` | You have {{available}} days of {{leaveType}} available. Shorten the request or choose another type. |
| `validation:date_before_start` | Enter an end date on or after the start date. |

Rules:

- One key per distinct meaning. Don't reuse `common:actions.submit` for "Submit claim" and "Submit request"; the specific label is part of the copy rules.
- Never build sentences by concatenating keys. Use interpolation with named values.
- Status keys use the **exact enum values** from `docs/03-architecture/DOMAIN-MODEL.md` section 4. Error keys use the **exact `code`** from `docs/05-backend/API-STANDARDS.md`. A CI check fails when an enum value or error code has no English key.
- Field-level validation keys use the field issue `code` (Zod issue code or custom code from `@hrm/contracts`) under the `validation` namespace.
- Interpolated values are formatted before interpolation (section 5) or with i18next formatters bound to the same functions; never insert raw ISO strings or decimal strings.

## 3. Plurals

Use i18next plural suffixes (`_one`, `_other`) driven by `Intl.PluralRules`:

```json
{
  "preview": {
    "workingDays_one": "{{count}} working day",
    "workingDays_other": "{{count}} working days"
  }
}
```

Bangla has the same two CLDR categories (`one`, `other`), so the structure carries over. Half-day counts (`0.5`) use `_other` ("0.5 days").

## 4. What is not translated

- Data entered by users (names, reasons, comments, leave type names configured by HR, department names).
- Codes (`EMP-0001`, `LV-000123`, run numbers).
- The company name and the product name "HRM".
- Server `title` and `detail` in problem responses (developer-facing English).
- Email templates are rendered on the server; their translation lives in `packages/mailer` (`docs/05-backend/EMAIL.md`).

## 5. Formatting dates, numbers and money

All formatting goes through `apps/web/src/lib/format.ts`, which wraps `Intl` and `date-fns` with `@date-fns/tz`. Components never call `toLocaleString`, `Intl.*` or `format()` directly.

| Function | Input | Output (`en`) | Notes |
|---|---|---|---|
| `formatDate(d)` | `YYYY-MM-DD` | 22 Oct 2026 | Plain date, no timezone conversion |
| `formatDateShort(d)` | `YYYY-MM-DD` | 22 Oct | Same year contexts |
| `formatDateRange(a, b)` | two dates | 3 to 5 Nov 2026 | CONTENT-STYLE.md section 8 |
| `formatMonth(y, m)` | year, month | November 2026 | Payroll periods |
| `formatTime(ts)` | ISO UTC timestamp | 9:12 am | Converted to the company timezone |
| `formatDateTime(ts)` | ISO UTC timestamp | 22 Oct 2026, 9:12 am | Company timezone |
| `formatRelative(ts)` | ISO UTC timestamp | 2 days ago | Under 7 days only, else `formatDate` |
| `formatDuration(min)` | minutes | 8h 05m | |
| `formatDays(n)` | decimal string | 2.5 days | Uses plural keys |
| `formatMoney(amount, currency)` | decimal string, `"BDT"` | ৳ 45,000.00 | Section 5.1 |
| `formatNumber(n)` | integer | 1,250 | |

- **Timezone**: timestamps are converted to the company timezone from settings (default `Asia/Dhaka`, FR-ORG-007), never the device timezone, so an HR user travelling sees the same times as the office.
- **Plain dates** (`work_date`, leave dates, `effective_from`) are calendar dates with no timezone. Parse them with `parseISO` into a date-only value and never pass them through `new Date('2026-10-22')`, which is UTC midnight and can shift a day.
- **Week start**: Sunday (D-005) in calendars and date pickers.

### 5.1 Money

- Input is the API's decimal string and currency (`"45000.00"`, `"BDT"`).
- `formatMoney` splits the string into integer and fraction parts and formats the integer part with `Intl.NumberFormat` grouping using `BigInt`, so no floating-point conversion happens. It always shows 2 decimals.
- Symbol: `৳` followed by a thin space (U+2009). English grouping: `45,000.00`.
- Negative values: `-৳ 1,200.00` with the line item labelled "Deduction" (COMPONENT-SPECS.md section 22).
- `MoneyInput` accepts `45000`, `45,000`, `45000.5` and normalises to a 2-decimal string before validation; it rejects more than 2 decimals.

## 6. Bangla readiness checklist

Ready in v1 (enforced now):

- No hard-coded strings in components (Biome or ESLint rule `i18next/no-literal-string` scoped to JSX text and `aria-label`, `title`, `placeholder` props).
- Layouts tolerate 30% longer text: no fixed-width buttons or badges; truncation with a tooltip only in table cells.
- Fonts: the font stack is built so a Bengali font can be appended without code changes (`--font-body: "Inter", "Noto Sans Bengali", Arial, sans-serif` when Bangla ships; Noto Sans Bengali is free, OFL, self-hosted).
- All formatting goes through `format.ts` with a locale parameter.

Decided when Bangla ships (owner decisions, see open questions):

- **Digits**: Bangla digits (০১২৩৪৫৬৭৮৯) via `Intl.NumberFormat('bn-BD')` or Latin digits in Bangla text. `format.ts` will accept a `numberingSystem` option (`beng` or `latn`) from user preferences; codes and IDs always stay Latin.
- **Grouping**: `bn-BD` uses South Asian grouping (৪৫,০০০ and ১২,৩৪,৫৬৭). Payroll exports for finance may keep international grouping regardless of UI locale.
- **Calendar**: Gregorian only in v1; the Bangla calendar (Bangabda) is not planned.
- Translation of leave type names configured by HR (would need per-locale names in the data model).

## 7. Workflow for adding text

1. Write the English copy following CONTENT-STYLE.md.
2. Add the key to `packages/i18n/locales/en/<namespace>.json`.
3. Use `t()` (or `<Trans>` for inline markup such as a link inside a sentence).
4. CI runs the missing-key and unused-key checks for `en`. `bn` is reported but not enforced until Bangla is enabled.
